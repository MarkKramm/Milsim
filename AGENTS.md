## What this project is

A living military base simulation. Personnel act autonomously, systems create
persistent consequences, and the player commands **by exception** — setting
policy, inspecting, and intervening only when it matters.

The player never micromanages. They watch, understand why things happen, and
make a small number of meaningful choices.

**The one question the whole prototype exists to answer:**

> Is it enjoyable to watch a small autonomous base operate, understand why things
> happen, and occasionally change a policy?

## What is decided — do not re-litigate these

The design is settled. `docs/LOCKED_DECISIONS.md` has full rationale for each.
They are called **settled**, not locked: the developer approved most by trusting
a recommendation rather than by item-by-item confirmation, so any can be
revisited. See the note at the top of that file.

Four external reviews have been completed and their corrections applied - see
`docs/REVIEW_REPLIES.md`. Between them they found eleven genuine errors in this
plan, eight of them contradictions introduced while fixing earlier reviews. Do not
reintroduce any of them. The most important: **readiness is a pure summary that
no system may read** - the underlying conditions drive behaviour. Enforced as
invariant 12 in `SYSTEM_DEPENDENCIES.md`.

1. **Stakes:** a "readiness" value drifts down when people are hungry, tired, or
   idle; at zero, people quit. Injuries are a later layer.
2. **Player agency:** concrete named-option decisions, not sliders. They queue
   in the report and rarely interrupt.
3. **Normal days:** small anomalies generated by simulation rules, never
   scripted story beats.
4. **Pacing:** 1 tick = 1 in-game minute; 1440 ticks per day; 8 ticks/sec at 1×
   → an in-game day is ~3 real minutes. Speeds: pause / 1× / 4× / 16×.
5. **Display:** abstract time ("Day 3 — Afternoon"), no live clock.
6. **No dithering:** workers finish or explicitly abandon a task; abandoning
   forfeits progress.
7. **Pressure:** time-based first, people-based later. Raids/war deferred.
8. **Stack:** TypeScript + Vite + React, played in a phone browser.
9. **Architecture:** the simulation is a pure module — no UI, no DOM, runnable
   headless.
10. **Determinism:** one seeded RNG stream from tick zero. No `Math.random()` in
    simulation.
11. **Layout:** panels only. No grid or map.
12. **Save/load:** the whole state must be plain JSON-serializable from the start;
    the actual save UI waits until Stage 3.

## The one rule that governs everything

> **The simulation contains no UI code.** `src/sim/**` must not import React or
> the DOM. If a React component contains a rule about how the world works, that
> is a bug.

Enforced by `tools/headless.ts`, which runs N ticks with no browser. That file
must keep working forever. If it ever has to be deleted or stubbed to make a
feature work, the architecture has broken — fix that first.

## What was built: Stage 2

Seven named people work two jobs in two facilities. Every roster row says what
the person is doing **and why**. One control — Balanced / Maintenance first /
Meals first — changes which queue the base attacks, and the effect is visible as
a backlog that moves.

Work arrives on a fixed cadence; jobs are claimed by whoever is free and eligible,
in id order, following the documented selection ladder. Deferred work persists
across days. Nothing in the simulation draws randomness except naming the roster.

**Gate to pass before Stage 3:** watch Days 4–5 on the phone, change the priority,
and understand why the backlog moved. Full protocol in
`docs/plans/STAGE2_MASTER_PLAN.md` §8.2. At least **3 of 4** evidence items.

Reproduce it without a browser:

```bash
npm run headless -- --ticks 7200 --priority meals-first
```

## How to work on this project

**Gates, not deadlines.** There is no schedule. Each stage has an exit gate that
is an *observation*, not a feature list, and since the first external review
every gameplay gate requires **observable evidence**: you must be able to say
yes to at least three of four specific questions (`docs/ROADMAP.md` §Gate
evidence). You may not advance past a stage that is not yet interesting, however
much you want to build the factory layer.

**The two ways this project dies:**

1. **Advancing past a gate that isn't met.** Building systems on an unverified
   assumption that the base simulation is fun. The original version of this plan
   wrote its gates as feelings and could be lied to — that has been fixed.
2. **Drift.** A passion project with no deadline dies when months go into
   systems that were never played.

**Scope is sequenced, not banned.** Combat, vehicles, faction warfare, hiring,
pathfinding, and animation are all fully designed in
`docs/GAME_DESIGN_BLUEPRINT.md` and all parked with defined unlock points. If you
suggest adding one, check its unlock condition in `docs/ROADMAP.md` first.

**Write down disagreements.** The original plan was audited and found to be a
good simulation design but an incomplete *game* design — no stakes, no goal, no
failure. That kind of critique is valuable and should continue. State the cost
of a change plainly; do not silently alter scope.

## Environment

- Development happens on an **Android phone in Termux**. A desktop is currently
  unavailable.
- The game is played in the **phone browser** via a Vite dev server.
- Node v24 and git are installed.
- **Code must stay in Termux home** (`~/military-base-sim-dev`), never on shared
  storage (`/storage/emulated/0`). Shared storage is a FUSE mount where
  `node_modules` is slow and file watching breaks.
- Docs are mirrored to `/storage/emulated/0/Download/military-base-sim/` for
  reading on the phone. **That mirror is a copy — never edit it directly, never
  put it in git.** Edit `docs/`, then sync.
- The developer is a **beginner/intermediate developer**. Explain unfamiliar
  tooling rather than assuming it.
